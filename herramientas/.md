# Arquitectura de Infraestructura para Herramientas de Inteligencia Artificial

Este documento define la arquitectura y separación de capas para la infraestructura de herramientas de Inteligencia Artificial y automatización. El objetivo es estructurar de manera modular y mantenible los componentes globales, los repositorios de desarrollo y las configuraciones específicas por proyecto.

---

## 1. Estructura General de Capas

Para garantizar una correcta separación de incumbencias, la infraestructura se divide en tres capas principales:

1. **Herramientas Globales:** Configuraciones, hooks y ajustes reutilizables en cualquier entorno de trabajo.
2. **Herramientas por Proyecto:** Configuración y dependencias específicas acopladas al ciclo de vida de un repositorio particular.
3. **Código Fuente de Skills:** Entorno de desarrollo, versionado y empaquetado (`.skill`) de las capacidades personalizadas.

---

## 2. Esquema de Directorios

### A. Repositorio de Infraestructura y Desarrollo (`herramientas-ia/`)
Este repositorio actúa como el "taller" centralizado, independiente del contenido académico o de proyectos de software específicos.

```text
herramientas-ia/
├── claude-skills/                        ← Código fuente de las skills (editable, sin empaquetar)
│   ├── mapa-conceptual-apuntes/
│   │   ├── SKILL.md
│   │   ├── references/
│   │   └── assets/
│   ├── mapa-conceptual-interasignaturas/
│   ├── guia-repaso-preparcial/
│   ├── flashcards-repaso-espaciado/
│   ├── informe-laboratorio/
│   ├── resumen-papers-aiaa/
│   ├── gestor-bibliografia/
│   ├── asistente-tfg/
│   ├── dist/                             ← Artefactos .skill empaquetados para distribución
│   └── CHANGELOG.md                      ← Historial de cambios y versionado de cada skill
│
├── claude-code-config/                   ← Configuración global para Claude Code (~/.claude/)
│   ├── settings.json
│   ├── hooks/                            ← Scripts de automatización (ej. inicialización de Graphify)
│   └── CLAUDE.md                         ← Directivas y lineamientos globales
│
├── herramientas-terceros/                ← Integraciones de terceros (ej. Graphify)
│   └── graphify/
│       ├── README-uso.md                 ← Documentación de comandos, versión y notas técnicas
│       └── proyectos-activos.md          ← Registro de adopción por repositorio
│
└── README.md                             ← Índice general, arquitectura y guía de instalación
```

### B. Estructura Interna por Proyecto (`<nombre-proyecto>/`)
Cada proyecto productivo o académico mantiene su propia configuración aislada y resultados generados:

```text
<nombre-proyecto>/
├── .claude/
│   ├── skills/          ← Subconjunto de skills requeridas específicamente por el proyecto
│   └── settings.json    ← Configuración local (sobreescribe la configuración global si es necesario)
├── graphify-out/         ← Resultados generados por Graphify (específicos del codebase)
└── ...                   ← Código fuente o contenido del proyecto
```

## 3. Principios de Diseño y Justificación

1. **Separación entre Fuente y Distribución:**  
   El desarrollo y mantenimiento de las skills se realiza sobre el código fuente (`claude-skills/<nombre>/`). Una vez estabilizadas, se empaquetan en la carpeta `dist/`. Esto evita editar directamente binarios o archivos empaquetados (`.skill`).

2. **Modularidad Global vs. Local:**  
   Herramientas de análisis estructural como **Graphify** operan de forma local sobre cada codebase para generar artefactos (`graphify-out/`). Por el contrario, las configuraciones transversales y hooks se centralizan para su reutilización inmediata en nuevos entornos.

3. **Control de Versiones y Trazabilidad (`CHANGELOG.md`):**  
   Dado el ciclo de iteración continua de las capacidades y automatizaciones, el uso de un registro de cambios por skill garantiza la claridad sobre las versiones desplegadas en los distintos entornos de chat y ejecución.

4. **Independencia del Ciclo de Vida Académico/Productivo:**  
   El repositorio de infraestructura (`herramientas-ia/`) se mantiene independiente de los repositorios de contenido (como la carrera aeroespacial o proyectos de desarrollo). De esta forma, se evita la contaminación cruzada en el historial de control de versiones (`git log`).
